# INMORE — web

Production foundation for the INMORE website. React + JavaScript, Vite,
React Three Fiber. Entirely client-side: no backend, no database, no CMS.

```bash
npm install
npm run dev      # http://localhost:5173
npm run build    # → dist/
npm run preview  # serve the production build
```

---

## What this is

The site is built around one idea: **design becoming something physical**. The
centrepiece is the studio at `/studio`, where a visitor uploads their own logo,
places it on a real product and turns it in their hands. Everything else on the
site leads to or from that moment.

The current version is complete enough to present and structured to continue
into production directly. Where approved brand assets, photography, copy or
product models are still outstanding, the code has a real, named place for them
rather than filler.

## Architecture

```
src/
├─ app/            Routing shell, error boundary, scroll behaviour
├─ pages/          One file per route
├─ components/
│  ├─ layout/      Header, footer
│  └─ ui/          Button, Slider, Section, Reveal, Wordmark
├─ features/
│  ├─ studio/      The "Test your product" experience
│  │  ├─ state/    Reducer + provider — all interaction state
│  │  └─ components/
│  └─ marketing/   Hero product presentation
├─ three/          Everything inside the WebGL boundary
│  ├─ ProductViewer.jsx   Canvas — the DOM/3D boundary
│  ├─ Stage.jsx           Lighting, shadows, camera controls
│  ├─ ProductModel.jsx    Config → geometry resolution
│  └─ models/             GLB loader, proxy geometry, availability probe
├─ lib/
│  ├─ artwork/     Loading, auto-trim, compositing, proof export
│  └─ utils/       Maths, formatting, class names, page meta
├─ i18n/           Locale provider, config, and one content module per language
│  └─ content/    en.js / ar.js — identical shape, translated strings
├─ products/       Product configuration registry
└─ styles/         Design tokens + global styles
```

### The separation that matters

- **`lib/artwork/`** knows nothing about React or three.js. It turns an image
  and a placement into a canvas.
- **`features/studio/state/`** knows nothing about rendering. It is a plain
  reducer plus the side effects around file loading.
- **`three/`** knows nothing about the DOM above `ProductViewer`. It receives a
  product, a texture and a flag.
- **`products/`** is data. It is the only thing that changes when the catalogue
  grows.
- **`i18n/content/`** is copy. No string a visitor reads lives in a component.

The 2D placement preview and the 3D texture are generated by the *same*
compositor, so the two views cannot disagree about where the artwork sits.

## Adding a product

1. Copy `src/products/paperCup.js` and edit it: dimensions, camera framing,
   print area, specs, guidance.
2. Register it in `src/products/index.js`.
3. Put its `.glb` in `public/models/` — see the requirements in
   `public/models/README.md`.

No application code changes. The picker, the studio, the contact form's product
list and the proof export all read from the registry.

## Product models

Product configs point at their production GLB from day one. Until a file is
present the studio probes for it, finds nothing, and falls back to reference
geometry that implements the same print contract — so the experience is fully
usable and presentable while models are being approved. Drop the approved file
in and the switch is automatic.

`public/models/README.md` documents the mesh naming, UV layout, units and
export settings the loader expects.

## Languages

English and Arabic, switched from the header. The choice persists in
`localStorage` and can be forced with `?lang=ar` for sharing and QA.

`src/i18n/content/en.js` is the shape every locale implements: ids, routes,
order and hrefs are structural and identical across languages; only readable
strings are translated. A missing translation is therefore a visible shape
mismatch rather than an English string silently leaking into an Arabic page.
There is a parity check worth running after any content edit:

```bash
node -e "Promise.all([import('./src/i18n/content/en.js'),import('./src/i18n/content/ar.js')]).then(([a,b])=>{const w=(x,y,p='')=>{for(const k of Object.keys(x)){if(!(k in y))console.log('missing:',p+k);else if(x[k]&&typeof x[k]==='object'&&!Array.isArray(x[k]))w(x[k],y[k],p+k+'.');else if(Array.isArray(x[k])&&x[k].length!==y[k].length)console.log('length differs:',p+k)}};w(a.default,b.default);console.log('ok')})"
```

Products carry their own translations in a `translations` block beside their
geometry, because a product is one physical thing; `useLocalizedProduct`
resolves the readable fields and leaves everything else alone.

### Direction

`LocaleProvider` sets `lang` and `dir` on the document element and everything
follows from there. Layout uses CSS logical properties (`inset-inline`,
`padding-inline-start`, `text-align: start`) rather than left and right, so
mirroring is automatic. The handful of places that genuinely need a physical
direction — a gradient's angle, a centring `translateX`, the underline's
transform origin — carry an explicit `[dir='rtl']` override.

Arabic is caseless and has a taller x-height, so it does not merely swap the
font: `:root[lang='ar']` retunes tracking, line height and the uppercase label
treatment. Latin runs inside Arabic text (emails, `250 × 92 mm`, file names)
are wrapped in `.u-ltr`, which isolates them so their punctuation does not
reorder.

Adding a third language: add an entry to `src/i18n/config.js` and a content
module beside `en.js`.

### Locale URLs

Locale lives in a provider, not the path. `resolveInitialLocale()` in
`src/i18n/config.js` is the single place that decides which locale a visit
gets — when Arabic later needs real `/ar/*` URLs for search indexing, that
function reads the path segment and nothing else in the app changes.

## The studio on touch

Below 1080px the studio switches from a page with a side panel to an app
shell: the product is pinned to the upper screen and the controls live in a
bottom sheet with three snap points and Product · Artwork · Place tabs.

The reason is specific. In a scrolling layout the controls and the product are
never on screen together, so a visitor drags a slider and cannot see what it
did — which removes the only thing the studio is for. The sheet publishes its
height as `--sheet-h`, the viewer reserves exactly that much room, and the
product resizes as the sheet moves. The top snap stops well short of full
height, and the viewer has a floor, so the product can never be buried.

Other touch affordances: pinch to resize the artwork and one finger to move it
in the print preview, a wheel gesture for the same on pointer devices, 44px
minimum targets under `@media (pointer: coarse)`, and the stage hiding its own
labels via a container query once it gets short.

Both layouts render the same components with the same state — `PointerStudio`
and `TouchStudio` in `src/pages/Studio.jsx` decide arrangement only.

## Design tokens

`src/styles/tokens.css` is the single source for colour, type scale, spacing,
motion and elevation. The accent colour and type stack are provisional; an
approved brand system replaces the values there without touching components.
Adding `class="on-paper"` to a section inverts the palette to the light
"paper" surface.

## Approval-state notes

Deliberate structures, not placeholders:

- **Work** entries carry real shape (client type, discipline, scale, year) and
  become case studies when photography and client sign-off land.
- **Contact** composes a complete enquiry email client-side. Setting
  `VITE_CONTACT_ENDPOINT` switches it to a normal POST — no markup changes.
- **Arabic copy** is a first, reviewable draft in Modern Standard Arabic,
  written to match the English register. It is in one file for a native
  reviewer to work through end to end.
- **Upcoming products** appear in the picker as unavailable rather than being
  hidden, so the range reads honestly while models are prepared.

## Deliberately not built

Authentication, CMS, database, admin dashboard, payments, quote management.
The frontend is arranged so each can be added behind an existing seam:
`i18n/content/` and `products/` are the CMS boundary, the contact form is the
enquiry boundary, and the studio's reducer already holds everything a saved
configuration or quote would need to serialise.

## Browser support

Modern evergreen browsers with WebGL 2. If the 3D layer fails, the error
boundary keeps the rest of the site usable.
